## 1. General Assessment

Architect's technical staging in `05-tech-options.md` is a massive win for software quality. Decoupling **Stage 1 (Zotero Ingestion + History Log + Notes + Obsidian Export)** from **Stage 2 (PDF Viewer & Anchoring)** isolates external integration risks before introducing canvas rendering complexity. 

However, several proposed mechanisms—specifically per-device log files with distributed deletion markers and deferred shell compatibility testing—introduce severe testability hazards that must be addressed before implementation begins.

---

## 2. Strongest Objections & Risks

### Objection 1: The "Erase Marker" (Decision 4) is an Untestable Distributed Trap
* **The Risk:** Architect proposes an "erase requested" marker to allow users to "forget a paper's history" across synced devices. In an asynchronous, peer-to-peer sync topology (Dropbox, Syncthing, Git), distributed deletion without consensus is a classic split-brain generator. What happens if Device B was offline for 30 days, created 40 new annotations, and then receives an erase marker from Device A? Does the marker wipe Device B's work? Testing this across arbitrary sync latency and clock skews requires full Jepsen-style chaos testing that is completely disproportionate for an MVP.
* **Alternative I Defend:** **Local-Only Purge in MVP.** "Forget history" must simply delete the local device's sidecar files on the current machine and cease tracking. Defer cross-device deletion tombstones to post-v1.0.

### Objection 2: Deferring the Tauri Shell Checkpoint to Stage 2 (Decision 2) is a Schedule Bomb
* **The Risk:** Architect proposes picking Tauri now and running a "one-day PDF rendering test on all three web views at Stage 2 start, switching to Electron if it fails." If WebKitGTK on Linux fails to render PDF.js canvases reliably at the start of Stage 2, switching to Electron means throwing away months of Rust IPC bindings, build pipelines, and packaging configurations.
* **Alternative I Defend:** **Run the Webview Rendering Spike in Week 1, Not Stage 2.** A minimal Tauri window loading PDF.js with a 50 MB PDF can be tested on Linux (WebKitGTK), Windows (WebView2), and macOS (WKWebView) in under 4 hours right now. If Linux fails the spike, we pivot to Electron *before* writing Stage 1 IPC code.

### Objection 3: Zotero Local API (Decision 6) Cannot Be Tested in CI Without a Mock Harness
* **The Risk:** Relying on a live Zotero instance (`127.0.0.1:23119`) prevents running integration tests on headless CI runners (e.g. GitHub Actions `ubuntu-latest`). If the local API schema changes in Zotero 7.1, tests will silently rot.
* **Alternative I Defend:** **Contract-First Mock Server (`tests/mocks/zotero_mock.rs`).** Before building the importer, capture raw HTTP fixtures from real Zotero 7 libraries and build a lightweight mock HTTP server for automated CI pipelines.

## 3. Decisions I Strongly Endorse from a QA Lens

1. **One-Way Obsidian Export (Decision 7):** Replacing live two-way projection with a deterministic, user-triggered file write eliminates ~90% of file-watcher race conditions, Windows file-locking collisions, and infinite sync loops.
2. **Dropping Auto-Update in MVP (Decision 9):** Avoids testing complex multi-OS update state machines, corrupted delta rollbacks, and privilege escalation vectors. Installers with published checksums are trivial to verify in clean container smoke tests.
3. **Per-Device Line Files for Append Merging (Decision 4):** Writing strictly to `<paper>/<device_id>.jsonl` eliminates local write lock contention and file-sync merge conflicts. Union reading is easily validated via property-based permutation testing (`proptest`).

## 4. Early Validation Protocols (Spikes QA Demands Before Building)

To prevent late architectural surprises, QA requires three automated spikes in Phase 1:

| Spike ID | Scope & Verification Target | Pass / Fail Metric |
| :--- | :--- | :--- |
| **SPIKE-1: Zotero Contract** | Run test script against live Zotero 7; verify item schema: page, quads, color, quote, comment. | All 5 fields present on 100% of tested highlights. |
| **SPIKE-2: Tauri Webview Canvas** | Load 50 MB / 500-page PDF via PDF.js in minimal Tauri window across Ubuntu, Windows, macOS. | Page 1 renders in < 1.5 s with 0 canvas text clipping on all 3 OSes. |
| **SPIKE-3: Log Merge Permutation** | Generative test (`proptest`): Feed 10,000 randomized events across 5 simulated device files into merge reader. | 100% commutative: `merge(A, B, C) == merge(C, B, A)` with identical output state. |
